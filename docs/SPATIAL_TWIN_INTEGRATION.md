# Spatial Twin Integration — SYNERGY Economic Digital Twin

**Date:** 16 November 2026  
**Status:** read-only integration contract and research backlog; no live economic API or financial settlement.

## 1. Purpose

Connect the SINERGY Economic Digital Twin to the SYNERGY world/EAEU spatial platform without changing the current economic model's accounting assumptions or making synthetic values appear to be measured regional data.

The spatial platform answers:
- where a region, cell, facility or transport corridor is located;
- which source dataset describes its physical geometry;
- when that geometry was observed/updated;
- what its CRS, accuracy, coverage and license are.

The economic model answers:
- what is produced, consumed, invested, transported or held in stock;
- what financial obligations and balanced postings exist;
- which values are observed, calibrated, derived, simulated or forecast;
- what the result of a reproducible scenario run is.

Neither platform should infer facts that belong to the other system.

## 2. Important current model boundary

The current README describes a five-country EAEU model, eight aggregated sectors and a set of investment directions. The five countries are real jurisdictions; many production capacities, technological coefficients and behavioural parameters are synthetic or partially calibrated. The model explicitly states that it is not a validated digital twin of the five national economies.

Therefore:
- do not draw modelled capacities as observed facility capacities;
- do not label synthetic production as actual production;
- do not extrapolate national totals to exact city/municipal locations;
- do not treat an economic cell marker as a property boundary, legal entity or ownership claim;
- do not use the map as a source of economic validation.

## 3. Stable spatial identity

Use independent identifiers for the following entities:

| Entity | Stable key | Notes |
|---|---|---|
| Country | ISO 3166-1 numeric and alpha-2 | Country membership and geometry are separate facts |
| Region | provider namespace + source feature ID + dataset release | Administrative codes can change; keep source lineage and version |
| EconomicCell | SYNERGY internal cell_id | Not an administrative boundary or jurisdiction |
| Facility | internal facility_id + source references | One facility may occupy several footprints or have multiple buildings |
| TransportEdge | graph namespace + edge ID + version | Do not assume two routing engines have identical edge IDs |
| ScenarioRun | run_id + model version + parameter hash + seed | Results are simulation output, not measured activity |

H3 or another spatial index may be stored as an auxiliary location index. It must not replace country, administrative, cadastral, legal or economic-cell identifiers.

## 4. Event interface

The shared event envelope is defined in:

- [SYNERGY geo-economic event schema](https://github.com/Shtenco/synergy_metaverse/blob/work/global-world-platform-foundation-20261116/schemas/geo-economic-event.schema.json)
- [Spatial Economic Twin contract](https://github.com/Shtenco/synergy_metaverse/blob/work/global-world-platform-foundation-20261116/docs/ECONOMIC_TWIN_CONTRACT.md)
- [Economic spatial bridge prototype](https://github.com/Shtenco/synergistic_economics/tree/work/spatial-economic-bridge-20261116/prototype)

Allowed evidence types remain distinct:
- observed — externally or operationally measured fact with a source;
- derived — deterministic transformation of cited source facts;
- simulated — output generated by a model run;
- forecast — forward-looking model output;
- demo — illustrative placeholder that must not be displayed as a real metric.

Every event requires source identity, source version, license, retrieval time, evidence type and a data-classification level. Where the event has a physical flow and financial posting, keep them as separate subrecords with separate units and references.

## 5. Physical and financial separation

A production quantity in tonnes, MWh, cubic metres or service units is not a monetary amount. A financial posting does not prove that a physical delivery occurred. Both may reference the same shipment, contract or project, but each must be reconciled by its own subsystem.

The existing economic accounting kernel remains authoritative for balanced debit/credit journals. The spatial adapter validates and links posting references; it does not post journals, settle transfers, create money, mint tokens or change the model's balances.

The existing Stage-B SCCE physical economy and household layers must preserve their own stock-flow invariants. A map event cannot bypass these checks.

## 6. Read-only map projection

The first integration stage is read-only:
1. publish validated country/region/cell identities and geometry;
2. expose aggregated economic metrics with data date, source, status and scenario run;
3. permit the map UI to select an entity and inspect its evidence/provenance;
4. allow users to compare observed and simulated layers without overlay ambiguity;
5. prohibit map clicks from issuing trades, changing ownership or posting financial entries.

Any future write-back must use a separately authorized API, transactional event key, audit record, access policy and explicit confirmation. It must not be implemented as a side effect of a visual interaction.

## 7. Regional aggregation rules

- Never place household-level financial, health, labour or personal-location information on public maps.
- Apply minimum-contributor suppression to small aggregates.
- Store both the geographic boundary version and the aggregation method.
- A cell crossing a state/region boundary must be explicitly split, assigned by a documented rule or represented as a multi-region entity; never silently assigned to the nearest centroid.
- Do not compare metrics from different geographic vintages without a documented concordance.
- Mark all synthetic and scenario data with a visible model version, run ID, seed and scenario label.

## 8. Integration sequence

### Phase A — registry synchronization
- ISO country registry and EAEU membership are versioned.
- Region geometry IDs retain source namespace, source release and geometry checksum.
- EconomicCell IDs are independent of any H3 level or administrative code.

### Phase B — observed-data overlay
- Start with aggregated, licensed and source-backed indicators.
- Store value, unit, period, source, transformation and validation status.
- Show missing-data coverage explicitly; no interpolation without a labelled method.

### Phase C — scenario overlay
- Publish scenario output only with run ID, model commit, config hash and seed.
- Different economic regimes use the same geographic aggregation and display scales.
- Separate scenario output from observed time-series layers in both style and query API.

### Phase D — physical asset twin
- Connect a facility only when a stable facility ID and permitted source geometry exist.
- Link production/resource/transport events by event reference, not by approximate visual proximity.
- Reconcile physical stock and financial postings separately.

### Phase E — controlled operations
- Add authorization, tenant boundaries, immutable audit, replay-safe writes and rollback/compensation semantics.
- Commission an independent security, data-rights and accounting review before any real operational write path.

## 9. Acceptance tests

- A simulated event can never be serialized as observed.
- A duplicate event ID or idempotency key is rejected before state mutation.
- Physical quantity and financial amount remain in separate schema branches and use their own units.
- An unbalanced journal is rejected by the accounting kernel.
- A region or cell without a verified geometry remains unlocated rather than being assigned a fabricated point.
- Small-group public aggregates fail closed.
- Map read-model refreshes do not change the source economic model.
- Scenario results can be reproduced from model version, parameter hash and seed.

## 10. Explicit non-goals

This document does not claim:
- that the current country-level EAEU model is empirically calibrated;
- that every production firm, building, route or household is mapped;
- that a map layer proves ownership or collateral;
- that asset visualization creates new economic value;
- that higher token price, turnover or monetary balances prove higher real output;
- that the SYNERGY map currently writes to any live ledger or payment system.
